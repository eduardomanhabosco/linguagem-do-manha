Problema 1 — Especificação formal dos tokens

Notação: expressões regulares no estilo JFlex/Python: | = união, * = zero ou mais, + = um ou mais, ? = opcional, [a-z] = classe de caracteres, [^x] = qualquer caractere menos x, \. = o ponto literal. Atenção: nos slides da Aula 3, + significa união; aqui, união é |.

Alfabeto: Σ = { a–z, A–Z } ∪ { 0–9 } ∪ { _ " . , ; ( ) { } + - * / % = ! < > & | \ } ∪ { espaço, tab, quebra de linha }. Letras acentuadas só valem dentro de texto e de comentário.

a) Palavras reservadas

RESERVADA = gambiarra | remendo | mostra | pega | se | senao | enquanto | firme | quebrado

Cada palavra é uma linguagem de uma palavra só, e a união delas é regular. São todas minúsculas e diferenciam maiúsculas: Se é identificador. Todas também casam com a ER de identificador; o conflito é resolvido no Problema 2a.

b) Identificadores

LETRA = [a-zA-Z_]        DIGITO = [0-9]
ID    = LETRA (LETRA | DIGITO)*          ≡  [a-zA-Z_][a-zA-Z0-9_]*

Começa obrigatoriamente com letra ou _ (assim 2abc nunca é identificador) e continua com letras, dígitos ou _. Sem acento, porque o C gerado não aceita acento em nome de variável. Aceita fita, _ok, total_2; rejeita 2abc, preço, a-b (este último vira três tokens: a, -, b).

c) Números inteiros e reais

NUM_INT  = DIGITO+                     ≡  [0-9]+
NUM_REAL = DIGITO+ \. DIGITO+          ≡  [0-9]+\.[0-9]+

O inteiro é uma sequência de um ou mais dígitos. O real tem exatamente um ponto, com pelo menos um dígito de cada lado. 3.4.5 não é gerado pela ER (teria dois pontos), nem 5. ou .5. O sinal negativo não faz parte do número: -5 são dois tokens (MENOS e NUM_INT), e o parser trata o menos unário. Assim, x-5 continua sendo uma subtração.

d) Operadores aritméticos, relacionais e lógicos

ARITMETICO = \+ | - | \* | / | %
RELACIONAL = == | != | >= | <= | > | <
LOGICO     = && | \|\| | !

+, * e | são escapados com \ porque são operadores da própria notação de ER. Os de dois caracteres aparecem antes dos de um (ver Problema 2b).

e) Atribuição, delimitadores e pontuação

ATRIB = =        DELIMITADOR = \( | \) | \{ | \} | ; | ,
TEXTO = " ( [^"\\\n] | \\[nt"\\] )* "

= guarda um valor e == compara (Problema 2b). Parênteses agrupam expressões e condições; chaves delimitam o programa e os blocos; ; termina cada comando; , separa os itens do mostra. O texto fica entre aspas duplas, não pode quebrar linha e aceita os escapes \n \t \" \\.

f) Espaços, quebras de linha e comentários

BRANCO        = [ \t\r\n]+
COMENT_LINHA  = // [^\n]*
COMENT_BLOCO  = /\* ( [^*] | \*+ [^*/] )* \*+ /       (no código: /\*[\s\S]*?\*/)

São reconhecidos e descartados (não viram token). O comentário de linha vai de // até o fim da linha. O de bloco vai de /* até o primeiro */ e pode ter várias linhas. A ER formal descreve "qualquer coisa que não contenha */"; no código, o quantificador preguiçoso *? faz o mesmo. As quebras de linha dentro dos comentários também são contadas para a posição.

Simulação de 3.4.5: q0 –3→ q1 –.→ q2 –4→ q3 –.→ sem transição. O léxico não aceita e acusa "número malformado". Simulação de 10.5: q0 –1→ q1 –0→ q1 –.→ q2 –5→ q3 (final): aceita.

Problema 2 — Resolução de conflitos e tratamento léxico

O léxico tem uma tabela de regras (nome, ER). Em cada posição do texto, as regras são testadas em ordem e a primeira que casa ganha (é o que o re.match do Python faz, e também a alternância |: re.match("=|==", "==") devolve =). A ordem da tabela resolve os conflitos abaixo.

a) Prioridade de reconhecimento: palavra reservada × identificador

se, enquanto e as outras reservadas também são palavras da linguagem de ID. Em vez de uma regra por reservada, usamos a técnica clássica (Aho, cap. 3): casar o lexema com a ER de identificador e depois consultar a tabela PALAVRAS_RESERVADAS. Se o lexema estiver lá, o token é a palavra reservada; senão, é ID. Vantagens: vale o maior casamento (senaozinho é ID inteiro, e não senao + zinho), e acrescentar uma palavra reservada é só uma linha na tabela.

def criar_token(nome, lexema, linha, coluna):
    if nome == "ID":
        tipo = PALAVRAS_RESERVADAS.get(lexema, TipoToken.ID)   # reservada? senão ID
        return Token(tipo, lexema, None, linha, coluna)

b) Maior casamento (longest match)

Entre as regras que casam numa posição, o lexema certo é o mais longo: >= é um token só, e não > seguido de =. Geradores como o Flex fazem isso sozinhos. No léxico manual, garantimos a mesma coisa pela ordem da tabela: os operadores de dois caracteres (== != >= <= && ||) vêm antes dos de um (= ! > <), e NUM_REAL vem antes de NUM_INT. Para números e identificadores, o próprio +/* da ER já consome o máximo, e as ERs terminam com (?![\w.]), que exige que o número acabe ali. Sem isso, 2abc viraria NUM(2) ID(abc) em vez de erro.

Sem o operador longo primeiro, x == 1 sairia como ID ATRIB ATRIB NUM, e o parser acusaria um erro que não existe.

c) Controle de posição (linha e coluna)

O léxico mantém três contadores: pos (índice no texto), linha (começa em 1) e coluna (começa em 1). Cada token (e cada erro) é criado com a linha e a coluna do início do lexema. Depois, os contadores avançam: se o lexema não tem quebra de linha, coluna += len(lexema); se tem (espaços com \n, comentário de bloco), linha soma o número de quebras, e a coluna passa a ser o número de caracteres depois da última quebra, mais 1. Assim a posição continua certa depois de comentários de várias linhas.

Problema 3 — Implementação

Arquivos: tokens.py (tipos de token e palavras reservadas), erros.py (ErroLexico com linha e coluna) e lexico.py (o analisador). Uso: python lexico.py arquivo.gam.

  • a) Entrada: lê um arquivo de texto (UTF-8; aceita arquivos com BOM).
  • b) Saída: imprime a sequência de tokens, um por linha, com linha:coluna, classe e lexema. Números já são convertidos (int/float) no campo de valor do token.
  • c) Erros: regras de erro na tabela reconhecem número malformado (2abc, 3.4.5, 5.), identificador com caractere fora de Σ (preço), texto sem fechar aspas, escape inválido, comentário de bloco sem fechar e, por último, o "pega-tudo" .: qualquer outro caractere (@, #, & sozinho) é erro. Cada erro registra linha, coluna e lexema, e a leitura prossegue depois do lexema problemático. Todos os erros aparecem no fim.
