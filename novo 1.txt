Esse arquivo é uma lista de regras para o léxico. O Rexical   O Rexical é um gerador de léxico mesmo papel do Flex para C.

  class Sample              ← nome do léxico que vai ser gerado
  macro
    BLANK   [\ \t]+         ← "apelido" para uma regex: 1 ou mais espaços/tabs
  rule                      ← a partir daqui: PADRÃO   →   O QUE GERAR
    {BLANK}                 ← espaço: sem ação = ignora
    \d+     { [:digit, text.to_i] }   ← dígitos → token digit (convertido pra número)

  end

    .       { [text, text] }          ← QUALQUER outro caractere → [ele, ele]

  text é o lexema, ou seja, o pedaço do código que a regex casou.
  
    💡 A última regra explica a sua dúvida anterior. O . pega qualquer caractere que sobrou ((, ), +, =…) e gera [text, text],
	
	
	 Exemplo: entrada soma = 42 + x

  ┌────────┬─────────────────┬──────────────────────────────────┐
  │ Pedaço │ Regra que casou │              Token               │
  ├────────┼─────────────────┼──────────────────────────────────┤
  │ soma   │ \w+             │ [:word, "soma"]                  │
  ├────────┼─────────────────┼──────────────────────────────────┤
  │        │ {BLANK}         │ (ignorado)                       │
  ├────────┼─────────────────┼──────────────────────────────────┤
  │ =      │ .               │ ["=", "="]                       │
  ├────────┼─────────────────┼──────────────────────────────────┤
  │ 42     │ \d+             │ [:digit, 42] ← número, não texto │
  ├────────┼─────────────────┼──────────────────────────────────┤
  │ +      │ .               │ ["+", "+"]                       │
  ├────────┼─────────────────┼──────────────────────────────────┤
  │ x      │ \w+             │ [:word, "x"]                     │
  └────────┴─────────────────┴──────────────────────────────────┘

  A ordem importa: 42 também casaria com \w+, mas \d+ vem antes e ganha. É por esse mesmo motivo que o enunciado fala de = vs ==: a regra de == tem que ser testada antes da regra de =, senão == vira dois =.

  No seu trabalho não precisa de Rexical nem de Ruby. Em Python a ideia é igual: uma lista de (regex, tipo) testada em ordem com o módulo re.

 Conceito 3: BNF e EBNF

   BNF (Backus-Naur Form)
    Os símbolos:
  - <Nome>: uma variável (não-terminal).
  - ::=: "é definido como". Faz o papel da flecha →.
  - |: "ou".
  - "HORA_DO_SHOW", com aspas: um terminal de texto fixo, como uma palavra reservada ou um símbolo.
  - id, num, string, sem aspas: um terminal que representa uma classe de token. O lexema varia (x, saldo, 42).

  - { X }: X repetido zero ou mais vezes (como o *).
  - [ X ]: X opcional, zero ou uma vez (como o ?).
  - ( X | Y ): agrupa, para poder usar o "ou" no meio de uma regra.

  
  - "BIRL" fecha três coisas: o programa, o if e o while. Funciona porque o parser sabe o que foi aberto. A escolha do delimitador de bloco é uma das "decisões próprias" que o enunciado sugere.

   Conceito 5: Ambiguidade e precedência


   No conceito 4 vimos que a árvore guarda a estrutura do programa. Agora vem o problema: e se um mesmo programa puder ter duas árvores?

   pode ser ou
     Esta parece a forma mais natural de descrever conta:
  <E> ::= <E> "+" <E> | <E> "*" <E> | num | "(" <E> ")"
  Com ela, 2 + 3 * 4 tem duas árvores:
   Árvore A: + em cima              Árvore B: * em cima
            E                                  E
        ┌───┼───┐                          ┌───┼───┐
        E  "+"  E                          E  "*"  E
        │   ┌───┼───┐                  ┌───┼───┐   │
      num 2 E  "*"  E                  E  "+"  E num 4
            │       │                  │       │
          num 3   num 4              num 2   num 3

   2 + (3 * 4) = 14                    (2 + 3) * 4 = 20

    São os mesmos tokens, com dois significados e dois resultados. Uma gramática assim é ambígua: existe pelo menos um programa com mais de uma árvore de derivação (ou, o que dá no mesmo, com mais de uma
  derivação mais à esquerda). Para um compilador isso é fatal, porque o C gerado dependeria de qual árvore o parser escolheu por acaso.

  
  É exatamente a gramática da BIRL-Lite:
  <Expressao> ::= <Termo> { ( "+" | "-" ) <Termo> }     ← nível do + e do −  (mais fraco)
  <Termo>     ::= <Fator> { ( "*" | "/" ) <Fator> }     ← nível do * e do /
  <Fator>     ::= id | num | "(" <Expressao> ")"        ← números, variáveis e parênteses (mais forte)

    A regra geral: quanto mais fraco o operador, mais perto da raiz fica a regra dele, e o que está mais fundo na árvore é calculado primeiro. Os parênteses são a única forma de "furar" os andares, e por isso (2
  + 3) * 4 continua possível.



  ┌────────────────┬─────────────────────────────┐
  │     Andar      │         Operadores          │
  ├────────────────┼─────────────────────────────┤
  │ 1 (mais fraco) │ OU                          │
  ├────────────────┼─────────────────────────────┤
  │ 2              │ E                           │
  ├────────────────┼─────────────────────────────┤
  │ 3              │ NÃO                         │
  ├────────────────┼─────────────────────────────┤
  │ 4              │ relacionais == != > >= < <= │
  ├────────────────┼─────────────────────────────┤
  │ 5              │ + -                         │
  ├────────────────┼─────────────────────────────┤
  │ 6              │ * /                         │
  ├────────────────┼─────────────────────────────┤
  │ 7 (mais forte) │ número, variável, ( )       │
  └────────────────┴─────────────────────────────┘

  
  Esse else é de qual if? Em C isso é ambíguo na gramática, e a linguagem resolve com uma regra extra ("o else fica com o if mais próximo"). A BIRL-Lite não tem esse problema, porque todo ELE_QUER termina com
  BIRL, e aí sempre se sabe onde cada if acaba. Quando vocês desenharem o if da linguagem (uma das 3 decisões próprias), lembrem disso: ter um fechamento explícito evita a ambiguidade.
