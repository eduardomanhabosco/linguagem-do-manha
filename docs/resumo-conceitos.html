Visão geral

Do código ao programa rodando

O transpilador é uma linha de montagem. O código passa por estações, e cada uma faz uma pergunta. Se a resposta for "não", ela para e mostra um erro. Só no fim sai o C, e o gcc transforma esse C em programa.

Por que separar o transpilador em estações?

Cada estação faz uma coisa só, fica pequena e dá para testar sozinha. Na apresentação dá para mostrar a saída de cada uma (tokens, AST e C). E o enunciado exige que sintaxe e semântica fiquem separadas no código.

Estação 1 · Léxico

Análise léxica

O léxico lê o texto caractere por caractere e agrupa os pedaços em tokens. Cada token é um par [tipo, lexema]: o tipo é a classe (ID, NUM) e o lexema é o texto exato que estava no código (saldo, 42).

Minhas anotações

Lê toda a cadeia de caracteres e gera um significado quando um conjunto de caracteres assume um valor possível dentro da linguagem.

É tipo uma cascata, igual a um separador de moedas: os pedaços caem nos buracos, que são os tokens. A regra de == tem que ser testada antes da regra de =, pra não cair no buraco errado.

O exemplo do Rexical (anotado)

O Rexical é um gerador de léxico para Ruby; faz o mesmo papel do Flex para C. O arquivo é uma lista de regras "padrão → o que gerar":

class Sample              ← nome do léxico que vai ser gerado
macro
  BLANK   [\ \t]+         ← "apelido" para uma regex: 1 ou mais espaços/tabs
rule                      ← a partir daqui: PADRÃO   →   O QUE GERAR
  {BLANK}                 ← espaço: sem ação = ignora
  \d+     { [:digit, text.to_i] }   ← dígitos → token digit (convertido para número)
  \w+     { [:word, text] }         ← letras/palavras → token word
  \n                      ← quebra de linha: ignora
  .       { [text, text] }          ← QUALQUER outro caractere → [ele, ele]
end

text é o lexema, o pedaço do código que a regex casou. Entrada soma = 42 + x:

PedaçoRegra que casouToken
soma\w+[:word, "soma"]
(espaço){BLANK}ignorado
=.["=", "="]
42\d+[:digit, 42], número e não texto
+.["+", "+"]
x\w+[:word, "x"]

Pegadinha

Nas minhas anotações escrevi que a regra . { [text, text] } "simplifica a linguagem" e que íamos usar. Não vamos. Ela transforma qualquer caractere em token, até um @. No nosso léxico cada símbolo tem regra e nome próprios (ABRE_PAREN, MAIS…), e o "qualquer outro caractere" vira erro léxico, com linha, coluna e lexema. Depois do erro, a leitura continua (EI03, problema 3c).

  • A ordem importa: 42 também casaria com \w+, mas \d+ vem antes e ganha. No Flex o maior casamento é automático (a ordem só desempata); no léxico feito à mão em Python, a ordem das regras decide. A própria regex faz o mesmo: re.match(r"=|==", "==") devolve =.
  • Palavra reservada × identificador: while casa com a regex de identificador. O jeito comum é casar como identificador e depois consultar uma tabela de palavras reservadas.
  • ['(', '('] não são dois parênteses: é um token só, em que o tipo tem o mesmo nome do símbolo. No nosso trabalho, melhor nomear: [ABRE_PAREN, '('].
Como vocês garantem que >= vira um token só, e não > e =?

Pela regra do maior casamento. As regras são testadas em ordem, e os operadores longos (==, >=, <=, !=) vêm antes dos curtos.

Como while vira palavra reservada, e não identificador?

Casamos como identificador e consultamos a tabela de palavras reservadas. Se estiver lá, o token vira o da palavra reservada.

Gramática livre de contexto

A gramática diz como os tokens podem se combinar. Formalmente ela é G = (V, T, P, S).

(10) Expressao  → ( Expressao )
  • Por que expressão regular não basta: em ((2)) o número de ( tem que ser igual ao de ). Um autômato finito tem um número fixo de estados e não conta sem limite. É o aⁿbⁿ da Aula 3, com a = ( e b = ). A regra (10) resolve pondo a variável no meio: cada ( que entra obriga um ) a sair.
  • "Livre de contexto": o lado esquerdo de toda regra é uma variável sozinha, trocada do mesmo jeito em qualquer lugar. Por isso a gramática não sabe se uma variável foi declarada antes: isso depende do contexto, e fica para a semântica.
  • A gramática só enxerga o tipo do token (id, num). O lexema (x, 5) vai de carona e só é usado depois.

O teste dos tokens

Para saber se um erro é sintático ou semântico, troque cada nome e número pelo tipo do token. Se o erro continua visível, é sintático. Se sumiu, é semântico.

CE_QUER_VER (x); e CE_QUER_VER (y); viram os mesmos tokens, CE_QUER_VER ( id ) ;, então "y não declarada" é semântico. Já ((2)) e ((2) têm tokens diferentes, então o ) faltando é sintático.

Por que a gramática não verifica se a variável foi declarada?

Porque ela é livre de contexto. CE_QUER_VER (x); e CE_QUER_VER (y); viram a mesma sequência de tokens. Saber se y existe depende de outra parte do programa, o contexto. A teoria confirma: "declarar antes de usar" funciona como a linguagem {wcw}, que não é livre de contexto.

Estação 2 · Parser

BNF e EBNF

BNF e EBNF são o jeito padrão de escrever as regras da gramática no relatório. Elas dizem o mesmo que o conjunto P; só muda a escrita.

Minhas anotações

<Nome>: uma variável (não-terminal). ::=: "é definido como", faz o papel da flecha. |: "ou". "HORA_DO_SHOW", com aspas: terminal de texto fixo. id, num, string, sem aspas: classe de token, o lexema varia.

{ X }: zero ou mais vezes (como o *). [ X ]: opcional (como o ?). ( X | Y ): agrupa, para usar o "ou" no meio de uma regra.

"BIRL" fecha três coisas: o programa, o if e o while. Funciona porque o parser sabe o que foi aberto. O delimitador de bloco é uma das "decisões próprias".

BNF:   <Bloco> ::= <Comando> <Bloco> | ε
EBNF:  <Bloco> ::= { <Comando> }

A gramática completa da BIRL-Lite, do enunciado:

<Programa>    ::= "HORA_DO_SHOW" <Bloco> "BIRL"
<Bloco>       ::= { <Declaracao> | <Comando> }
<Tipo>        ::= "MONSTRO" | "TRAPEZIO"
<Declaracao>  ::= <Tipo> id [ "=" <Expressao> ] ";"
<Comando>     ::= <Atribuicao> | <Leitura> | <Escrita> | <Condicional> | <Repeticao>
<Atribuicao>  ::= id "=" <Expressao> ";"
<Leitura>     ::= "QUE_QUE_CE_QUER" "(" id ")" ";"
<Escrita>     ::= "CE_QUER_VER" "(" ( string | <Expressao> ) ")" ";"
<Condicional> ::= "ELE_QUER" "(" <ExprLogica> ")" <Bloco> [ "NAO_VAI_DAR" <Bloco> ] "BIRL"
<Repeticao>   ::= "NEGATIVA_BAMBAM" "(" <ExprLogica> ")" <Bloco> "BIRL"
<ExprLogica>  ::= <Expressao> <OpRel> <Expressao>
<OpRel>       ::= "==" | "!=" | ">" | ">=" | "<" | "<="
<Expressao>   ::= <Termo> { ( "+" | "-" ) <Termo> }
<Termo>       ::= <Fator> { ( "*" | "/" ) <Fator> }
<Fator>       ::= id | num | "(" <Expressao> ")"

Pegadinha

"(" com aspas é o token parêntese e aparece no programa. ( sem aspas é da notação: só agrupa e nunca aparece. Em "(" ( string | <Expressao> ) ")", o programa CE_QUER_VER ("oi"); tem um par de parênteses só. Sem o agrupamento, o | dividiria a regra inteira, e ela aceitaria CE_QUER_VER ("oi" sem fechar.

Relacional (OpRel)compara 2 valores== != > >= < <=verdadeiro/falso
Lógicojunta comparaçõesE, OU, NÃO (em C: &&, ||, !)verdadeiro/falso

A <ExprLogica> da BIRL-Lite só aceita uma comparação. O EI03 pede os operadores lógicos no léxico, então a recomendação é pôr E, OU e NÃO na gramática também.

A EBNF descreve mais linguagens que a BNF?

Não. Ela só abrevia. Todo { } ou [ ] pode ser reescrito em BNF com uma variável nova, recursão e ε.

Derivação e árvore de derivação

Derivar é trocar uma variável de cada vez pelo lado direito de uma regra, até sobrar só terminal. A árvore de derivação é o desenho disso.

Minhas anotações

A árvore é o que o parser realmente constrói.

Árvore de derivação × AST: a árvore de derivação guarda tudo, cada variável, cada parêntese e cada ;. A AST é a versão enxuta, só com o que importa para gerar o C.

  • ⇒ é um passo; ⇒* é "em zero ou mais passos".
  • Forma sentencial: passo intermediário, ainda com variáveis. Sentença: o resultado, só terminais.
  • L(G) = { w | S ⇒* w, com w só de terminais }: a linguagem é tudo o que dá para derivar a partir de S.

Derivação mais à esquerda de 2 + 3 * 4

Expressao
⇒ Termo + Termo
⇒ Fator + Termo
⇒ num + Termo
⇒ num + Fator * Fator
⇒ num + num * Fator
⇒ num + num * num

A árvore (a mesma para qualquer ordem)

               Expressao
          ┌────────┼────────┐
        Termo     "+"     Termo
          │           ┌─────┼─────┐
        Fator       Fator  "*"  Fator
          │           │           │
        num 2       num 3       num 4

A derivação mais à direita usa as mesmas regras nos mesmos lugares, só em outra ordem, e dá a mesma árvore. O 3 * 4 pendurado num Termo só mostra que ele é calculado antes da soma. O parser por descida recursiva faz sempre a derivação mais à esquerda.

Comece pela raiz, aplique a regra, desça um nível e repita até sobrar só terminal:

Ambiguidade e precedência

Uma gramática é ambígua quando um mesmo programa tem duas árvores. A precedência se resolve com um "andar" (uma variável) por nível: o operador mais fraco fica perto da raiz, e o que está mais fundo é calculado primeiro.

A gramática "natural" <E> ::= <E> "+" <E> | <E> "*" <E> | num | "(" <E> ")" dá duas árvores para 2 + 3 * 4:

 Árvore A: + em cima              Árvore B: * em cima
          E                                  E
      ┌───┼───┐                          ┌───┼───┐
      E  "+"  E                          E  "*"  E
      │   ┌───┼───┐                  ┌───┼───┐   │
    num 2 E  "*"  E                  E  "+"  E num 4
          │       │                  │       │
        num 3   num 4              num 2   num 3

 2 + (3 * 4) = 14                    (2 + 3) * 4 = 20

A solução é a gramática da BIRL-Lite, com um andar por precedência. Os parênteses são o "elevador" que volta ao andar de cima:

<Expressao> ::= <Termo> { ( "+" | "-" ) <Termo> }     ← andar do + e do −  (mais fraco)
<Termo>     ::= <Fator> { ( "*" | "/" ) <Fator> }     ← andar do * e do /
<Fator>     ::= id | num | "(" <Expressao> ")"        ← números, variáveis e parênteses

Com ela, a árvore B não existe: o Fator teria que gerar 2 + 3 sem parênteses, e ele não gera. O enunciado exige isso: a precedência tem que estar na própria estrutura sintática e na AST, e não ser corrigida depois pelo gerador.

Por que Expressao, Termo e Fator separados?

Cada nível de precedência é uma variável. O * só aparece dentro do Termo, então em 2 + 3 * 4 o 3 * 4 só pode ficar agrupado embaixo: sobra uma única árvore. Com E → E + E | E * E a gramática seria ambígua, com duas árvores e dois resultados (14 e 20).

Associatividade e recursão à esquerda

Associatividade decide a ordem entre operadores do mesmo andar. 10 - 3 - 2 é (10 - 3) - 2 = 5, e não 10 - (3 - 2) = 9: o − e o / são associativos à esquerda.

Minhas anotações

Trabalhando com | abre margem para recursão à esquerda e à direita. Damos um ' e trocamos a ordem. A esquerda é ruim porque não temos critério de parada. Na conversão à direita, comparamos primeiro com o alfa. Não queremos, para não ter loop infinito.

Em limpo:

  • Em BNF, a árvore pende para o lado da recursão. E → E - num (à esquerda) dá (10 − 3) − 2, que é o certo.
  • Mas na descida recursiva a recursão à esquerda trava: expressao() chama expressao() antes de consumir qualquer token. Não há critério de parada, e o resultado é um loop infinito (RecursionError no Python). Recursão em si não é o problema: Fator → ( Expressao ) consome o ( antes e está tudo bem.
  • A transformação do livro ("damos um ' e trocamos a ordem"): A → A α | β vira A → β A' e A' → α A' | ε. Primeiro consome o β. Depois, cada A' compara o próximo token com o começo do α: se casar, consome e repete; se não, usa ε e para. Esse é o critério de parada.
  • Exemplo: E → E - T | T vira E → T E' e E' → - T E' | ε. Na EBNF da BIRL-Lite é simplesmente T { - T }.

O { } vira um while que acumula à esquerda

def expressao(self):
    no = self.termo()                        # 10
    while self.proximo() in ("+", "-"):
        op = self.consome(self.proximo())
        no = (op, no, self.termo())          # junta com tudo o que já tinha
    return no

Cuidado também com a recursão à esquerda indireta (A → B x com B → A y). O que vale conferir é se toda regra consome um token antes de voltar a si mesma.

Por que não usaram E → E + T?

Porque é recursiva à esquerda: na descida recursiva a função chamaria a si mesma sem consumir token, e o parser entraria em loop infinito. Usamos T { + T }, que vira um while que monta a árvore acumulando à esquerda, e a associatividade fica certa (10 - 3 - 2 = 5).

Estação 2 · Parser

Parser por descida recursiva

Cada regra da gramática vira uma função. O parser começa pela raiz e desce até as folhas (top-down), e escolhe a regra olhando só o próximo token, sem nunca voltar atrás. O nome técnico é LL(1).

Minhas anotações

O programa recebe uma sequência de tokens e transforma essa sequência numa representação de árvore. O parser tem um "dedo" (pos) apontando o token atual: proximo() espia o tipo sem avançar; consome(tipo) confere e avança, e se não for o tipo esperado é erro sintático.

Vídeo: This Simple Algorithm Powers Real Interpreters: Pratt Parsing (Core Dumped, em inglês).

Sobre o vídeo

Ele explica o Pratt parsing, outra técnica top-down para expressões com precedência, que usa uma "força de ligação" para cada operador em vez de um andar por nível. É ótimo para entender a ideia. No trabalho usamos a descida recursiva com Expressao, Termo e Fator, que bate uma a uma com a gramática do relatório.

def consome(self, tipo):                  # confere o tipo e avança o dedo
    if self.proximo() != tipo:
        self.erro(repr(tipo))             # erro sintático (conceito 8)
    self.pos += 1
    return self.tokens[self.pos - 1][1]   # devolve o lexema

# <Declaracao> ::= <Tipo> id [ "=" <Expressao> ] ";"
def declaracao(self):
    tipo = self.consome(self.proximo())   # MONSTRO ou TRAPEZIO
    nome = self.consome("id")
    valor = None
    if self.proximo() == "=":             # [ ] vira if
        self.consome("=")
        valor = self.expressao()
    self.consome(";")
    return ("Declaracao", tipo, nome, valor)

As chamadas de função formam a árvore de derivação: programa() chama bloco(), que chama declaracao(), que chama expressao(), termo() e fator().

  • Um token basta porque cada alternativa começa diferente. Se dois comandos começassem com id, seria preciso espiar 2 tokens ou reescrever a gramática (fatoração à esquerda).
  • Dica para a nossa linguagem: cada comando começando com a sua própria palavra-chave, e o id sozinho só na atribuição.
  • Por que o BIRL fecha três coisas: o bloco() para quando vê um token que não inicia comando, e quem abriu (o programa, o if ou o while) consome o seu BIRL.
Como o parser sabe qual regra usar?

Ele olha o próximo token. Cada alternativa começa com um token diferente (o conjunto PRIMEIROS), então um token basta e ele nunca volta atrás. É LL(1).

Qual produção reconhece o if?

A <Condicional>, implementada na função condicional(). Com uma função por regra, a resposta é direta. É o maior argumento a favor da descida recursiva (o enunciado, §4, pede que o grupo saiba isso).

Estação 2 · Parser

Erros sintáticos

Erro sintático: os tokens existem (o léxico aceitou todos), mas a ordem não bate com nenhuma regra da gramática. É o "comeu gato o".

Minhas anotações

Guardar o erro e a posição dele para o retorno. Colocar aqui a diferença entre erro sintático e léxico.

LéxicoSintáticoSemântico
Perguntaas palavras existem?a ordem está certa?faz sentido?
ExemploMONSTRO x @ 2;MONSTRO x = ;CE_QUER_VER (y);
Mensagemlinha, coluna e o caractere inválidolinha, token encontrado e o esperadonome da variável e regra violada
Depois do errocontinua lendo (EI03, 3c)para no primeiro (§4)para (e nunca gera C)
Erro sintático (linha 3, coluna 13): esperava um número, uma variável ou '(', mas encontrei ';'
  • O erro é detectado no consome() (veio outro token) ou num ponto de escolha (o token não serve para nenhuma alternativa). O LL(1) acusa no primeiro token impossível, então a posição é precisa.
  • Para ter linha e coluna, cada token leva a sua posição: (tipo, lexema, linha, coluna). É o controle de posição do EI03 (2c).
  • Classes de erro próprias (ErroLexico, ErroSintatico, ErroSemantico), e não o SyntaxError do Python. Assim os testes sabem qual estação acusou.
  • O léxico continua porque um caractere inválido não atrapalha o resto. O parser para porque, depois de um erro de estrutura, ele "perde o fio" e geraria erros falsos em cascata.

Pegadinha: o ; esquecido

Com MONSTRO x = 5 na linha 1 e CE_QUER_VER (x); na linha 2, o parser só percebe a falta do ; no próximo token, na linha 2. Melhor apontar a linha do token anterior: "linha 1: faltou ';' depois de '5'".

Por que o parser para no primeiro erro e o léxico não?

O enunciado pede assim, e faz sentido: um caractere inválido não atrapalha o resto da leitura, mas um erro de estrutura faz o parser perder o fio, e continuar geraria erros falsos em cascata.

Saída do parser

AST: árvore sintática abstrata

A AST guarda só o significado do programa: operadores, valores e comandos. É o que a semântica e o gerador percorrem.

Minhas anotações

Representação hierárquica, em forma de árvore, da estrutura semântica do código-fonte. Como é gerada: o código-fonte passa primeiro pelo analisador léxico, que transforma o texto bruto em partes individuais (palavras-chave, operadores, identificadores). Esses tokens são processados pelo parser, que verifica se está tudo na gramática da linguagem. Se for válido, constrói a AST: uma versão limpa, estruturada e significativa do código, sem a sintaxe irrelevante. Mostra a planta, o diagrama do código.

AST: 5 nós

     Mult

  • Some a pontuação (;, (, ), HORA_DO_SHOW, BIRL) e os nós em corrente (Expressao → Termo → Fator → num).
  • Os parênteses viram forma: o Soma fica embaixo do Mult porque havia parênteses.
  • "Abstrata": MONSTRO x = 5; e FICHA x = 5; viram a mesma AST, Declaracao(inteiro, x, 5). As fases seguintes nem sabem as palavras-chave.
  • Cada nó guarda a linha, para a semântica dizer onde está o erro.

À risca

O aviso do Classroom pede "analisador sintático funcionando, com árvore de derivação", e o enunciado pede a AST. Para cobrir os dois: uma opção que imprime a AST no formato do enunciado e outra que imprime as chamadas do parser indentadas, que são a árvore de derivação.

Qual a diferença entre árvore de derivação e AST?

A árvore de derivação mostra cada regra usada, inclusive a pontuação. A AST guarda só o significado, e os parênteses viram a forma da árvore. As fases seguintes usam a AST porque ela é menor e não depende das palavras-chave.

Estação 3 · Semântica

Análise semântica e tabela de símbolos

A semântica percorre a AST na ordem do programa, anotando cada declaração numa tabela de símbolos e conferindo cada uso de nome nela.

Minhas anotações

Guardar na tabela; se já teve, pega da tabela.

O enunciado (§5) pede: tabela com nome e tipo; erro para uso antes da declaração; erro para declaração duplicada no mesmo escopo; compatibilidade de tipos (conceito 11); mensagem clara; e a semântica separada do parser.

{"repeticoes": {"tipo": "inteiro", "linha": 2},
 "carga":      {"tipo": "real",    "linha": 3}}

Escopo por bloco: uma pilha de tabelas

  • Entrou num bloco (if, while): empilha uma tabela nova. Saiu: desempilha, e as variáveis do bloco somem.
  • Declarar: confere e anota só na tabela do topo (o "mesmo escopo").
  • Procurar: do topo para baixo, do mais interno ao mais externo.
  • É igual ao C gerado, em que cada { } tem o seu escopo. A linguagem e o C se comportam igual.
ProgramaErro
CE_QUER_VER (y);a variável y foi usada sem ser declarada
MONSTRO x = 1; e depois MONSTRO x = 2;x já foi declarada neste escopo (na linha 1)
MONSTRO x = x + 1;x usada sem ser declarada: o valor é conferido antes de declarar
bonus usada depois do BIRL do if onde nasceubonus usada sem ser declarada (saiu do escopo)

Decidir e escrever no relatório

Sombreamento: um bloco pode declarar um nome que já existe fora dele? Com a pilha é permitido, igual ao C. Dá para proibir, procurando em todos os escopos antes de declarar. O importante é decidir e registrar como regra semântica.

Como funciona o escopo no transpilador de vocês?

É uma pilha de tabelas: empilha ao entrar num bloco e desempilha ao sair. A declaração olha só o topo, e a busca vai do topo para baixo.

Estação 3 · Semântica

Tipos e compatibilidade

Toda expressão tem um tipo, e a semântica o descobre antes de rodar (tipagem estática), de baixo para cima na AST: o literal pelo formato, a variável pela tabela e a operação pela regra do operador.

        +  → real              real + real = real
      ┌─┴─┐
  carga    *  → real           inteiro * real = real
  (real) ┌─┴─┐
         2   1.5
      (int) (real)

Contas (+ - * /)

esq \ dirinteiroreal
inteirointeiroreal

Guardar valor em variável

variável ← valorinteiroreal
inteiro✅❌ perderia os decimais
real✅ 3 vira 3.0✅
  • Comparações: número com número, e o resultado é lógico. Texto com texto fica proibido: em C, "a" == "b" compara endereços, e não o conteúdo.
  • Tenha pelo menos um ❌. Se tudo for permitido, a verificação de tipos nunca acusa nada e não há erro de tipo para mostrar.
  • O tipo calculado fica anotado no nó. O gerador usa para escolher %d ou %f.
  • Tipos recomendados: inteiro e real, com texto só para mostrar mensagens. Variável de texto em C pede strcpy, strcmp e afins: não vale o risco em 2 semanas.

Pegadinha: divisão inteira

No C, 7 / 2 dá 3. Ou adotamos a regra do C e escrevemos no relatório, ou o / sempre dá real e o gerador escreve (float) 7 / 2.

Qual o tipo de 2 + 3.5, e como a semântica descobre?

Real. Se um lado é real, o resultado é real (promoção). A semântica calcula de baixo para cima: literal pelo formato, variável pela tabela, operação pela regra do operador.

Estação 4 · Geração

Geração de código: AST → C

Minhas anotações

É a última estação, e a mais "mecânica": as anteriores já fizeram o trabalho difícil. A gramática resolveu a estrutura, a AST a precedência e a semântica os nomes e tipos. O gerador só percorre a AST e escreve o C equivalente.

Só roda se léxico, sintaxe e semântica passaram. Tem que percorrer a AST: trocar texto (replace("MONSTRO", "int")) não vale, porque trocaria a palavra até dentro de um texto e não saberia escolher %d ou %f.

Nó da ASTC gerado
Declaracao(inteiro, x, 3)int v_x = 3;
Atribuicao(x, expr)v_x = expr;
Escrita(expr) inteira / realprintf("%d\n", expr); / printf("%f\n", expr);
Escrita(Texto)printf("%s", "texto");
Leitura(x) inteiro / realscanf("%d", &v_x); / scanf("%f", &v_x);
Se(cond, entao, senao)if (cond) { … } else { … }
Enquanto(cond, corpo)while (cond) { … }
BinOp(op, esq, dir)(esq op dir)

As quatro armadilhas

  1. Parênteses sempre em toda BinOp: o C segue a estrutura da AST sem depender das regras de precedência dele.
  2. Prefixo v_ em todas as variáveis: uma variável chamada printf ou int não quebra o C.
  3. Texto com printf("%s", …): um % dentro do texto não vira formato.
  4. float e não double: com double o scanf exige %lf.
#include <stdio.h>

int main(void) {
    int v_repeticoes = 3;
    float v_carga = 10.5;
    while (v_repeticoes > 0) {
        printf("%d\n", v_repeticoes);
        v_carga = v_carga + (2 * 1.5);
        v_repeticoes = v_repeticoes - 1;
    }
    if (v_carga >= 15) {
        printf("%s", "Treino concluido!\n");
    } else {
        printf("%s", "Ainda falta carga.\n");
    }
    return 0;
}

Depois: gcc -Wall saida.c -o saida e saida.exe. Os .c dos testes válidos são entregáveis.

Como o gerador sabe se usa %d ou %f? E por que tantos parênteses?

Pelo tipo que a semântica anotou no nó. Os parênteses garantem que o C siga a mesma estrutura da AST, onde a precedência já está resolvida.

    return avalia(no.esq) + avalia(no.dir)

def gera(no):      # GERADOR (o nosso): escreve a conta         → "(2 + 3)"
    return f"({gera(no.esq)} {no.op} {gera(no.dir)})"
  • Um transpilador é um compilador: tem as mesmas fases, só muda o alvo. O primeiro compilador de C++, o Cfront, era um transpilador que gerava C.
  • Front-end (léxico, sintático, semântico) é o que vocês programam. Back-end: o nosso gera C, e o gcc faz o resto (otimizar, gerar o executável). É o modelo da BIRL original.
  • Por que C: preserva explicitamente tipos, expressões, printf/scanf, if/else e laços (enunciado, §1).
O que vocês fizeram: um compilador ou um transpilador?

Um transpilador, que é um tipo de compilador. Tem as mesmas fases de análise, mas o alvo é outra linguagem de alto nível (C) em vez de código de máquina. O gcc faz a etapa final e prova que a tradução está certa.
